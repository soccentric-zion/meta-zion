# Hardware secure boot (CSU / PUF / eFUSE) — status

**This is documentation only. Nothing in meta-zion automates any of this,
and nothing should.**

## What already works (separate trust boundary)

Zion-OS already has a complete, working signing chain for **OTA payloads**:
`zion-swupdate-config` verifies `.swu` package signatures using
`swupdate-public.pem` (RSA-4096), generated by
`scripts/generate-swu-keys.sh`. That protects against a tampered/untrusted
update package being installed by `swupdate`.

That is a **different, already-solved problem** from hardware secure boot.
It says nothing about whether the boot chain itself (FSBL → PMU firmware →
ATF → U-Boot) that eventually runs `swupdate` was itself authentic and
unmodified.

## What's a placeholder: CSU chain-of-trust

The ZynqMP CSU (Configuration Security Unit) provides:

- **Secure boot authentication/encryption** — RSA/ECDSA-signed and
  AES-GCM-encrypted boot images (FSBL, PMU firmware, ATF, U-Boot, PL
  bitstream), verified by boot ROM before anything else executes.
- **PUF (Physically Unclonable Function)** — device-unique key material
  derived from SRAM startup behavior, used to wrap the actual boot keys so
  they're never stored in the clear.
- **eFUSE** — one-time-programmable storage for the root-of-trust key hash,
  boot-mode locks, and anti-rollback counters.

None of this is implemented in meta-zion, and it should **not** be
automated into a Yocto recipe or a Makefile target:

- eFUSE programming is **irreversible** — a mistake permanently and
  unrecoverably bricks the specific physical board's secure-boot
  capability. There is no "undo."
- It requires per-device key provisioning (each board's PUF is unique),
  which doesn't fit a shared OS image build pipeline the way OTA signing
  keys do.
- AMD/Xilinx's own tooling (`bootgen`, already available via
  `meta-xilinx-tools` for BOOT.BIN generation) requires deliberate,
  human-supervised key-generation and fusing steps, run once per device
  during provisioning — not per build.

## To make this real

This would be a provisioning-time procedure (documented runbook + a human
operator with physical board access), not a build-time recipe:

1. Generate an authentication keypair and (optionally) an encryption key
   using `bootgen`'s key-generation flow.
2. Build an authenticated/encrypted `BOOT.BIN` with `bootgen`, referencing
   those keys (already partially staged: `meta-xilinx-tools` ships
   `bootgen` itself; only the authentication/encryption *usage* is
   missing).
3. On a per-device basis, run the PUF registration flow and program the
   key hash + boot-mode lock eFUSEs, following AMD's documented procedure
   (UG1283) — deliberately outside of any automated Zion-OS tooling.

If this becomes a real requirement, it should be scoped as its own
project (a provisioning runbook + supervised tooling), not folded into
`make image kr260`.
